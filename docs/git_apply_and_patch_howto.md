# Using `git apply` and `patch`: A Practical Guide

This document explains how to work with patch files using `git apply` (Git-native) and the classic Unix `patch` command. It focuses on the typical workflow of taking a diff (e.g., from ChatGPT/Codex or another developer) and safely applying it to your repository.

---

## 1. Overview: When to Use What

### `git apply`

- Applies a unified diff/patch **to your working tree** (and optionally the index).
- Does **not** create a commit; you commit separately.
- Git-aware: understands paths like

    ``` `a/` and `b/` from `git diff`/`git show`. ```

### `patch`

- Classic Unix tool; operates on plain files, with no Git awareness.

- Needs the correct `-pN` strip level to match your file paths.

- Useful outside a Git repo or when the patch paths don’t match Git’s expectations.

### git am

- Applies an **email-style patch** created by `git format-patch`.

- Creates a **commit** automatically, preserving the original author, message, etc.

- Not covered in detail here, but worth knowing it exists for email-based workflows.

For most “ChatGPT/Codex gave me a diff, how do I use it?” situations, \`\` is the right tool.

---

## 2. Typical Workflow: Applying a Patch with `git apply`

### Scenario

You have a diff like this (from someone else, or generated by yourself):

```diff
diff --git a/tools/expand-questions.mjs b/tools/expand-questions.mjs
index 1234567..89abcde 100644
--- a/tools/expand-questions.mjs
+++ b/tools/expand-questions.mjs
@@ -10,6 +10,10 @@ function foo() {
   ...
 }
```

### 2.1 Step 1 — Save the patch to a file

From the repository root:

```bash
cd /path/to/your/repo

# Create a patch file and paste the diff into it
nano expand-questions.patch      # or vim, code, etc.
# Paste the entire diff (from 'diff --git' to the end), then save and exit.
```

**Validation:**

```bash
ls -l expand-questions.patch
```

You should see the patch file with a non-zero size.

---

### 2.2 Step 2 — Dry run / sanity check

```bash
git apply --stat expand-questions.patch
git apply --check expand-questions.patch
```

- `--stat` shows which files and how many lines will change.
- `--check` verifies that the patch can be applied cleanly (no changes yet).

**Validation:**

- If `git apply --check` returns **no output** and exits successfully, the patch is compatible.
- If errors appear, see [Section 7](#7-troubleshooting-when-patches-fail-to-apply).

---

### 2.3 Step 3 — Apply the patch

```bash
git apply expand-questions.patch
```

This updates your working tree (but does not stage or commit changes by default).

**Validation:**

```bash
git status
git diff -- tools/expand-questions.mjs
```

You should see the expected modifications. When satisfied:

```bash
git add tools/expand-questions.mjs
git commit -m "Apply patch to expand-questions.mjs"
```

---

## 3. Creating Patches with Git

### 3.1 From uncommitted changes

Generate a patch from your current unstaged or staged changes:

```bash
# All unstaged changes (relative to HEAD)
git diff > my-change.patch

# Only one file
git diff tools/expand-questions.mjs > expand-questions.patch
```

You can then apply this patch later (on another machine or branch) using `git apply`.

**Validation:**

```bash
wc -l my-change.patch
head my-change.patch
```

Confirm the patch is non-empty and contains a proper unified diff.

---

### 3.2 Between two commits or branches

```bash
# Differences between main and feature/my-branch
git diff main..feature/my-branch > feature.patch

# Differences between two specific commits
git diff abc123..def456 > bugfix.patch
```

**Validation:**

```bash
git apply --stat bugfix.patch
git apply --check bugfix.patch
```

If `--check` passes, the patch is structurally sound.

---

## 4. Applying Patches to the Index (Staging Area)

Sometimes you want to control whether changes go to:

- **Working tree only** (default),
- **Index only**, or
- **Both working tree and index**.

### 4.1 Index only (`--cached`)

Applies changes directly to the index, leaving the working tree untouched:

```bash
git apply --cached fix.patch
```

**Validation:**

```bash
git diff          # working tree vs index
git diff --cached # index vs HEAD
```

`git diff --cached` should show the patch, while `git diff` may be empty.

---

### 4.2 Working tree and index (`--index`)

Applies changes to both working tree **and** index:

```bash
git apply --index fix.patch
```

**Validation:**

```bash
git diff          # should be empty if index and working tree match
git diff --cached # shows changes staged for commit
```

---

## 5. Reversing an Applied Patch

If you have applied a patch but **not yet committed**, you can reverse it:

```bash
git apply -R expand-questions.patch
```

- `-R` tells Git to apply the patch in reverse.

**Validation:**

```bash
git status
git diff
```

The working tree should return to its previous state (no changes from that patch).

If the patch has **already been committed**, use:

```bash
git revert <commit_sha>
```

This creates a new commit that undoes the changes in the specified commit.

## 6. Using the Classic `patch` Command

The `patch` tool works outside of Git and can be useful when:

- You are editing files that are **not** in a Git repo.
- The patch paths don’t match the repo layout, and you want manual control via `-pN`.

A typical unified diff for `patch` looks like:

```diff
--- a/tools/expand-questions.mjs
+++ b/tools/expand-questions.mjs
@@ -1,5 +1,5 @@
```

### 6.1 Applying a patch with `patch`

From the directory that corresponds to the root of the paths:

```bash
# Test (no file changes)
patch --dry-run -p1 < expand-questions.patch

# Apply for real
patch -p1 < expand-questions.patch
```

- `-p1` strips the leading `a/` and `b/`, turning `a/tools/…` into `tools/…`.
- If your patch doesn’t have `a/` or `b/` prefixes, you might need `-p0` instead:

  ```bash
  patch --dry-run -p0 < expand-questions.patch
  patch -p0 < expand-questions.patch
  ```

**Validation:**

- Check command exit status (`echo $?`).
- Inspect the modified file(s) or run `git diff` if you are inside a repo.

---

### 6.2 Reversing a patch with `patch`

```bash
patch -R -p1 < expand-questions.patch
```

- `-R` applies the patch in reverse.

If a patch does not apply cleanly, `patch` can emit “Hunk FAILED” messages and write `.rej` files containing the rejected hunks for manual inspection.

---

## 7. Troubleshooting: When Patches Fail to Apply

### 7.1 With `git apply`

Always test first:

```bash
git apply --check my.patch
```

If you see errors like:

```text
error: patch failed: tools/expand-questions.mjs:123
error: tools/expand-questions.mjs: patch does not apply
```

Consider:

1. **Correct base**\
   Ensure you are on the branch/commit the patch was generated against:

   ```bash
   git status
   git log -5 --oneline
   ```

2. **Use ********\`\`******** for partial application**

   ```bash
   git apply --reject --whitespace=fix my.patch
   ```

   - `--reject` writes `.rej` files where hunks cannot be applied.
   - `--whitespace=fix` helps with trivial whitespace mismatches.

3. **Manual resolution**

   - Open the `.rej` and the target file.
   - Manually integrate the rejected changes.
   - Then `git add` and `git commit`.

---

### 7.2 With `patch`

If `patch` emits “Hunk FAILED” messages:

- Check any created `*.rej` files (contain the rejected hunks).
- Verify `-pN` is correct (`-p0` vs `-p1`).
- Ensure the file contents match the version the patch expected.

## 8. Common Pattern: “ChatGPT Diff → Your Repo”

When you receive a diff from ChatGPT/Codex and want to apply it safely:

```bash
cd /path/to/your/repo

# 1) Save the diff as a patch
cat > gpt-change.patch << 'EOF'
<PASTE FULL DIFF HERE (from "diff --git" to end)>
EOF

# 2) Dry run
git apply --stat gpt-change.patch
git apply --check gpt-change.patch

# 3) Apply
git apply gpt-change.patch

# 4) Review and commit
git diff
git status
git commit -am "Apply GPT patch for <short description>"
```

**Validation checklist:**

- `git apply --check` is clean (no errors).
- `git diff` shows only the intended changes.
- Tests / linters pass after the patch is applied.
- Commit message clearly describes what the patch does.

---

## 9. Summary

- Use \`\` for most Git-based patch workflows (especially diffs from `git diff`, `git show`, or ChatGPT).
- Use \`\` when working outside Git or when you need explicit control over path stripping (`-pN`).
- Always:
  - Save the patch to a file,
  - Run a **dry run** (`git apply --check` or `patch --dry-run`),
  - Review the changes with `git diff`,
  - Then commit with a clear message.

## 10. One-Window Bash Cheat Sheet (All Key Commands Together)

You can paste this entire block into a shell (and run pieces line by line) as a consolidated reference.

```bash
#!/usr/bin/env bash
# Cheat sheet: git apply / patch workflows

# === 0. Go to your repo root ================================================
cd /path/to/your/repo || exit 1

# === 1. Save a diff from ChatGPT/Codex into a patch file ====================
# Paste from "diff --git ..." through the end between EOF markers.
cat > gpt-change.patch << 'EOF'
<PASTE FULL DIFF HERE>
EOF

# Quick sanity check: patch file exists and is non-empty
ls -l gpt-change.patch
head -n 20 gpt-change.patch

# === 2. Dry run a patch with git apply =====================================
git apply --stat gpt-change.patch        # Show files/lines to be changed
git apply --check gpt-change.patch       # Validate patch applies cleanly

# === 3. Apply the patch to the working tree ================================
git apply gpt-change.patch

# Inspect changes
git status
git diff

# Stage and commit
git add -u
git commit -m "Apply GPT patch: <short description>"

# === 4. Generate patch files from your own changes ==========================
# 4.1 All unstaged changes → patch
git diff > my-change.patch

# 4.2 Single file → patch
git diff tools/expand-questions.mjs > expand-questions.patch

# 4.3 Between two branches/commits → patch
git diff main..feature/my-branch > feature.patch
git diff abc123..def456 > bugfix.patch

# Dry-run check for any generated patch
git apply --stat my-change.patch
git apply --check my-change.patch

# === 5. Apply patch to index/working tree variants ==========================
# 5.1 Index only (staging area; working tree untouched)
git apply --cached fix.patch

# 5.2 Working tree + index (staged immediately)
git apply --index fix.patch

# Check staged vs working tree
git diff          # working tree vs index
git diff --cached # index vs HEAD

# === 6. Reverse a patch (not yet committed) ================================
# Reverse a patch applied with git apply
git apply -R gpt-change.patch

# If the changes were already committed, revert the commit instead:
# git revert <commit_sha>

# === 7. Troubleshooting failed patches =====================================
# Check if a patch can apply at all:
git apply --check problem.patch || echo "Patch does not apply cleanly."

# Try with --reject to get .rej files for manual merging:
git apply --reject --whitespace=fix problem.patch

# Inspect recent commits & branch status for context
git status
git log -5 --oneline

# === 8. Using classic 'patch' outside Git (or when paths differ) ===========
# Test apply with patch (strip first path component "a/" or "b/")
patch --dry-run -p1 < some.patch

# Apply for real if dry-run succeeds
patch -p1 < some.patch

# If your patch has no "a/" / "b/" prefixes, try -p0 instead:
patch --dry-run -p0 < some.patch
patch -p0 < some.patch

# Reverse patch with classic 'patch'
patch -R -p1 < some.patch

# If hunks fail, .rej files may be created; inspect and merge manually.

# === 9. Standard post-patch validation =====================================
# Run tests / linters as appropriate for your project, e.g.:
# npm test
# pytest
# ./run-linters.sh

git status
echo "Done. Review above output and diffs before pushing."
```
